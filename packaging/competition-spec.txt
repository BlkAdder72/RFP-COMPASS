🔥 THE ANGLE THIS WEEK
Last comp was The Control. You ran the same questions with and without a folder and committed both. The Rebuild runs the same test on two versions of the same folder.

Three things separate a real rebuild from a second draft:
1. The original stays. Pinned at its judged commit, in the repo, untouched. If a mod cannot diff old against new, there is no rebuild to score.
2. The questions come from the feedback. Take the two fixes and the one thing that would have moved you up. Turn each into a question with a checkable answer. Commit questions.md before you change a line.
3. You report what did not improve. A rebuild that is better at everything is a rebuild nobody tested. Where did the new version tie. Where did it get worse. What did you leave alone on purpose and why.
The rebuild's quality is not the score. The gap closed against the feedback is. 💪

🗂️ THE METHODOLOGY
If this is your first comp, welcome. Here is what you need to know:
This week (and every week) you are learning interpretable context methodology. Folders as architecture. Each file does one job well.
Your repo has four parts at the root:
- 📁 original/: your judged entry, pinned at the commit we scored, read only
- 📄 feedback.md: the file we sent you, verbatim, or the public results post if you are rebuilding someone else's
- 📁 rebuild/: the new version, with the usual five files inside: identity, rules, examples, reference/, README
- 📊 results.md: what changed, question by question, including what tied or got worse, and what you chose not to touch
Plus the control:
- 📝 questions.md: five to ten questions derived from feedback.md, with expected answers, committed before rebuild/ exists
- 🧪 run-original/: raw transcript of the questions against original/, exact prompts included
- 🧪 run-rebuild/: raw transcript of the same questions against rebuild/, same order
Write the questions. Commit. Run them against the original. Commit. Rebuild. Run them again. Commit. Write results. That is the whole method.
